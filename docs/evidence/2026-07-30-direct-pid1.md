# Direct mainline PID 1 evidence

Date: 2026-07-30

## Scope

This record covers the first persistent Linux 6.17 boot that was proven to
execute an active PID 1 directly from the OnePlus bootloader. It does not claim
a mounted postmarketOS rootfs, USB gadget support, SSH, or complete hardware
support.

## Fixed framebuffer mapping lifetime

The diagnostic framebuffer was initially mapped with `early_memremap()`. That
pointer remained stored after `early_ioremap_reset()`, so later milestone writes
used a mapping whose lifetime had ended. The direct-boot kernel now:

1. calls `early_memunmap()` before `paging_init()`;
2. clears the stale pointer;
3. obtains `phys_to_virt(0x9c000000)` after `paging_init()`.

The framebuffer reserved-memory node is not marked `no-map`, so the arm64 linear
mapping is valid after page-table initialization. Hardware then displayed the
post-init row that had previously been absent.

## Hardware result

The observed markers prove this ordered path:

1. `kernel_init_freeable()` reached its final instrumented stage;
2. the global async initramfs wait returned normally;
3. init memory and boot configuration were released;
4. PTI, RCU, and sysctl setup returned;
5. `kernel_execve()` succeeded;
6. all three EL1-to-EL0 transition markers executed;
7. PID 1 entered and returned from its first syscall;
8. PID 1 entered a second syscall and made at least 16 syscalls.

No OnePlus USB identity, mainline USB gadget, network interface, or SSH endpoint
appeared during the 240-second observation window.

## Bootloader command-line limit

The PID 1 syscall pattern did not begin with the static wrapper's `openat()`.
Disassembly proved that `openat()` is the wrapper's first syscall, while the
observed pattern matched a different init program.

The working R6 image provided the control. Its primary Android boot header
contains exactly 512 non-NUL command-line bytes and stores the remainder in
`extra_cmdline`. Runtime `/proc/cmdline` contains only the first 511 characters:
the image ends in `ramoops.co`, while Linux receives `ramoops.c` immediately
followed by the bootloader token `lk_version=V1.0`. The bootloader therefore:

- ignores header-v2 `extra_cmdline`;
- reserves the last byte of the primary field for termination;
- passes at most 511 image command-line characters.

The tested diagnostic had placed `rdinit=/hotdog-mainline-wrapper` at character
837. Linux never received it and correctly executed the original postmarketOS
`/init`. This explains both the sustained PID 1 activity and the absence of the
wrapper's `openat()` marker.

## First-511 command-line hardware result

The corrected 483-character command line was then tested on the HD1913. The
large PID 1 cells reported `0,1,2,4,6,7`, with `3,5` hollow. This proves that:

1. the bootloader passed `rdinit=/hotdog-mainline-wrapper`;
2. the static wrapper entered EL0 and returned from `openat()`;
3. `/dev/fb0` was unavailable to the wrapper;
4. the wrapper executed `/init`;
5. the postmarketOS init made at least sixteen system calls.

No USB device appeared during the 240-second observation window. The 300-second
userspace watchdog also did not return the phone to fastboot, which is
consistent with `/init` blocking before `hotdog_rescue_watchdog_start stage1`.
The prior run's ramoops area was registered by R6 but contained no records.

## Bounded udev follow-up candidate

The next candidate changes only the wrapped initramfs. It keeps the exact
kernel, DTB, and 483-character command line from the stage-two hardware result.
Each udev command is allowed 15 seconds. A command that remains blocked is
signaled and left behind without waiting on it, its return cell remains hollow,
and stage two continues toward USB and the rootfs. The final row reports:

6. entry into `setup_udev`;
7. return from `udevd -d --resolve-names=never`;
8. return from `udevadm trigger --type=devices --action=add`;
9. return from `udevadm settle`;
10. return from `setup_usb_network`.

The `udev-bounded` stage profile is generated by
`build-mainline-pmos-wrapper-initramfs.sh`, including an instrumented
`init_functions_2nd.sh` overlay. The current candidate additionally packages
the static APSS MMIO helper. PID 1 arms it for 32 seconds with the bootloader
restart reason, kicks it once per second until the 300-second logical deadline,
and disarms it only after the rootfs success marker. The
first hardware attempt reached Qualcomm `900e` before PID 1. Two bounded Sahara
reads, separated by a protocol-level reset, both returned a valid
Image-resident stage `400`, detail `986`, and restart reason `0x77665500`.
Stage 400 is written by `hotdog_finish_initcall_diagnostics()` after all 986
initcalls, immediately before the old 30-second watchdog was disabled. The
repeatable result identifies a deadline race rather than a regression in the
bounded udev initramfs.

An attempted 120-second follow-up also entered `900e` earlier, after about
24 seconds. The SM8150 APSS block implements a 20-bit timeout field:
`120 * 32764` wraps modulo `0x100000` to roughly 24 seconds. The superseding
candidate therefore uses the maximum non-wrapping 32-second value and disables
the early kernel watchdog before writing stage 400. That follow-up nevertheless
recorded valid stage `400`, detail `986`, before entering `900e`: kernel
initialization had completed, then the old PID 1 helper armed `330 * 32764`
ticks, which wraps to about 10 seconds. The rebuilt initramfs now uses a
32-second hardware interval with periodic kicks instead. The DTB, command line,
and stage helper remain unchanged. The candidate is offline/AVB validated and
pending hardware validation.

## Source handoff hardware result

The corrected 32-second periodic-watchdog candidate completed the kernel path
but filled only initramfs cells 0-5. No USB identity appeared, and neither the
300-second logical deadline nor the following hardware interval produced a
host-visible Fastboot return. A manual reset exposed Fastboot, after which the
prearmed host watchers restored the stock DTBO and R6 image.

The next diagnostic changed only the wrapped initramfs handoff: PID 1 sourced
`/init_2nd.sh` instead of executing it. A deep handoff profile then filled all
cells 0-10, proving this ordered path:

1. entry into the sourced second stage;
2. return from both function-library sources;
3. return from the stage-two watchdog call;
4. entry into `setup_udev`.

No direct-boot USB identity appeared, and the last screen state remained at
`setup_udev`. The periodic watchdog again failed to produce a host-visible
Fastboot return after more than eight minutes. This result validates the
sourced handoff as a useful diagnostic bypass, but does not by itself prove
that the second `execve` is the root cause: an earlier image had already
entered `init_2nd.sh`.

## Static fork/exec bounded-udev candidate

The shell-based bounded runner launches each command with `"$@" &` and only
starts its timeout after ash returns the background PID. The 9/11 hardware
result is consistent with the shell remaining suspended while the first
external `udevd` execution is blocked, before that timeout can begin. This is
a working hypothesis, not yet proof of the exact ash implementation path.

The next candidate changes only the wrapped initramfs. Each udev command now
runs through a static AArch64 helper that calls `fork()` before `execvp()`.
The parent measures a 15-second `CLOCK_MONOTONIC` deadline, terminates the
child process group with `SIGTERM` and `SIGKILL`, and returns status 124 to the
PID 1 shell. Its builder validates command success, exact exit-status
propagation, and a real timeout under QEMU. A deterministic second initramfs
build reproduced the same hash, and the helper extracted from the final boot
image matches the tested binary. Kernel, DTB, and command line are byte-identical
to the earlier 9/11 hardware candidate.
