# Haptics: AW8697 identification and r143 driver build - 2026-08-11

## Result

The haptics controller is reachable and identifies itself as an AW8697. Revision
`r143` adds a source-built device-tree binding and a minimal mainline-style
`FF_RUMBLE` driver. Driver, device tree, schema and strict postmarketOS package
builds pass. Physical vibration and feedbackd integration remain untested.

## What the stock tree says

Two haptics blocks are described:

```
soc/i2c@89c000/aw8697_haptic@5A     compatible = "awinic,aw8697_haptic"
soc/qcom,spmi@c440000/.../qcom,haptics@c000    the PM8150B block
```

`i2c@89c000` is `i2c7` upstream. The PM8150B path is a dead end for now:
mainline has no `qcom,*-haptics` driver at all, and the `INPUT_PM8XXX_VIBRATOR`
already in this configuration targets the older PMIC generation. The AW8697 is
what the stock actually drives.

The stock OnePlus R tree supplies the board wiring: address `0x5a`, reset on
GPIO 116 and interrupt on GPIO 24. It also identifies project 19801, which
selects the 170 Hz actuator profile. The 235 Hz profile in the vendor source is
specific to projects 19065 and 19161 and is therefore not used here.

## Driver sources

`linux-next` carries `drivers/input/misc/aw86927.c`, the same Awinic family. It
is not a drop-in:

| | upstream aw86927 | this part |
| --- | --- | --- |
| chip id | two bytes at `0x57`/`0x58` | one byte at `0x00` |
| values | `0x9270`, `0x9380` | `0x97` |

So it identifies a later generation. What it does give is the right skeleton:
regmap, soft reset by writing `0xaa` to `0x00`, standby through `SYSCTRL3`, and
the input force-feedback integration. The vendor driver in the published
OnePlus kernel, at `drivers/misc/aw8697_haptic`, supplies this generation's
register map, confirms `AW8697_CHIPID 0x97`, and provides the conservative
170 Hz continuous-mode values. The implementation uses those hardware values
but follows the mainline input-force-feedback structure; it does not import the
vendor Android control interface or require proprietary waveform firmware.

## The change and what it proves

`0128` enables the bus. Nothing else was enabling it, so the part could not be
reached at all. `0129` adds the binding and `0130` adds the driver, Kconfig,
device-tree node and `CONFIG_INPUT_AW8697_HAPTICS=y` package configuration.

On hardware, scanning the enabled Geni buses finds it and it answers with its
identity:

```
trouve 0x5a sur i2c-3
i2c-3 registre 0x00 = 0x97
```

Note that `i2c7` in the device tree enumerates as `i2c-3` at runtime; the Geni
and CCI controllers are numbered in probe order, so the DT alias and the
`/dev/i2c-N` number do not match. The four CCI buses belong to the cameras.

`0x97` is exactly the chip id the vendor driver expects, from a register the
upstream driver does not even read. That settles both questions at once: the
part is present and it is this generation.

## Implemented interface and limits

The driver:

- resets the part through active-low GPIO 116 and verifies the single-byte
  `0x97` identity at register `0x00`;
- exposes an input device with `FF_RUMBLE` through the kernel's memless force
  feedback interface;
- drives continuous mode with the HD1913 170 Hz profile;
- maps effect strength to the vendor profile's normal drive ceiling of 60 and
  uses the corresponding overdrive value of 125;
- returns the controller to standby when an effect stops or the driver is
  removed.

The interrupt wiring is described for the complete board contract, although
the first bounded continuous-mode implementation does not consume interrupts.

## Offline verification

The target driver compiles with `W=1`. The Hotdog DTB compiles and its flattened
tree contains the `haptics@5a` node. The new binding passes `dt_binding_check`;
that run reports only pre-existing type warnings in the unrelated camera lens
binding. `git diff --check` and the strict pmbootstrap package build pass.

## Hardware validation still required

The phone was not visible through USB, fastboot or SSH after the build, so no
physical vibration is claimed. The first hardware run should identify the new
input event node, issue one short low-strength pulse, then test full strength
and repeated stop/start behavior. Only after those checks should feedbackd be
enabled and notification or interface feedback be marked working.
