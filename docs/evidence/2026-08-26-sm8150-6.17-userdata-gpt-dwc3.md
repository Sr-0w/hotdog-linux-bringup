# SM8150 6.17 full userdata GPT and DWC3 teardown evidence

Date: 2026-08-26

This note records the first complete-image boot of the clean 6.17 migration.
It is hardware evidence, not a release manifest.

## Nested GPT correction

The r8/r36 full image was written to `userdata` together with its matching AVB
`boot_b`. Recovery readback matched both candidate hashes. The first boot then
stopped in the postmarketOS initramfs because the nested GPT described only the
14,096,007,168-byte image while the physical userdata partition is
232,382,812,160 bytes.

`scripts/prepare-hotdog-userdata-gpt.py` now generates bounded primary, backup
and stale-backup patches for the real 4096-byte-sector device. After applying
and reading back those three regions, the debug initramfs reported:

```text
userdata physical bytes: 232382812160
logical sector bytes: 4096
pmOS root start LBA: 124928
kpartx partitions: userdata1, userdata2
```

This proves the installer-side GPT expansion. It does not resize or otherwise
rewrite the ext4 payload.

## Rootfs panic

Continuing from the debug shell reached the real rootfs, then faulted at about
65 seconds:

```text
dwc3 ... request ... was not queued to ep3in
Unable to handle kernel NULL pointer dereference at virtual address 0x178
```

The timing matches `hotdog-usb-acm`: the default-runlevel service unbinds the
active initramfs NCM configfs gadget before adding ACM. Linux 6.17 lacks the
upstream fix for concurrent `dwc3_remove_requests()` paths. During giveback the
DWC3 lock is temporarily released for the function callback, allowing another
path to complete and free the same request.

Kernel commit `d1584b678d01ed2797d26687c9d23e2793fca305` adds the upstream EP0 queued
state and completed-request guard. The source link for the accepted fix is:

<https://patch.msgid.link/20251120074435.1983091-1-manish.nagar@oss.qualcomm.com>

The resulting r9 package passes the full offline build and package validator:

| Artifact | Size | SHA256 |
|---|---:|---|
| kernel APK | 23,013,574 | `f14e903f0b70e383d60b77c944566e224088b0a5000c0ccef43911a27dde68f1` |
| packaged Image | 31,492,608 | `7b754e67435640ca870d485755b39e44736001fb3f16d68cdd71dd70c76130b9` |
| packaged DTB | 164,102 | `9d31fa35ecd38dfd560209e6fb7d93f32dbc71eadac2b349ed594b07a32b3b12` |

Hardware validation of r9 remains pending. Until it completes, r8 remains the
last electronically validated standalone kernel and the r8/r36 full image is a
diagnostic candidate, not a merge-ready image.

## Oracle comparison

The first r9 debug retry showed that the DWC3 backport alone was not a complete
image fix. A direct comparison against the immutable r181 checkpoint and the
last working package stack found the hidden composition differences:

- the successful standalone r8 boot and the failing r8/r36 full boot have
  byte-identical kernels and DTBs, but different ramdisks;
- the working ramdisk is based on the modern postmarketOS initramfs series,
  while the fresh full image was silently downgraded to `3.4.6-r2` by the old
  local pmaports fork;
- the old working rootfs does not run a service that unbinds the active USB
  gadget, while r36 introduced `hotdog-usb-acm` with exactly that behavior;
- the relevant USB DT contract is otherwise preserved: DWC3 still uses Apps
  SMMU stream `0x140`, both PHYs, the same suspend/LPM quirks and peripheral
  mode;
- the migrated config lost `USB_GADGET_VBUS_DRAW=900`,
  `V4L2_FLASH_LED_CLASS=m` and the TER16x32 framebuffer font.

The corrected composition therefore keeps the valid DWC3 race backport but no
longer relies on it to make an unsafe userspace sequence acceptable. A generic
`deviceinfo_usb_acm` flag creates NCM and ACM together before the first UDC
bind. The rootfs ACM service only starts a getty on the pre-created tty and
never writes configfs. Kernel revision r10 restores the three proven config
contracts above.

The clean pmaports input is upstream commit
`8d24be3f898eb8c717678ceb881972cc6b1c76f9`, with integration commit
`0d395b9ed6768cd51c7a48749e05efd5e325ac26`. It retains OpenRC explicitly so
the service-manager migration is not mixed into this kernel baseline.

## Corrected hardware result

The exact r10/r37 image was written as one atomic userdata/boot pair. Recovery
read back the complete 4,500,488,192-byte candidate and 96 MiB boot image with
matching hashes, then independently verified the primary, stale-backup and
physical-end backup GPT regions.

The normal boot reached SSH on kernel build `#11` with these package identities:

- `linux-oneplus-hotdog-mainline617-clean-6.17.0-r10`;
- `device-oneplus-hotdog-3-r37`, subsequently upgraded to `3-r38`;
- `postmarketos-initramfs-3.12.3-r2`.

The configfs configuration contained `ncm.usb0` and `acm.usb0` from the first
enumeration and reported `MaxPower=900`. No `request ... was not queued`, NULL
pointer or kernel panic appeared. Ninety samples over 15 minutes retained the
same USB identity, `/dev/ttyACM0`, ping and SSH.

The generic qbootctl OpenRC script did mark slot B successfully but reported a
false crashed state because it backgrounds a oneshot command. Device r38
replaces it with a synchronous, localmount-ordered bounded service. A fresh
software reboot changed boot ID, returned to SSH, kept both gadget functions,
left the generic service out of the runlevel and reported
`hotdog-qbootctl: started`; both A/B slots remained bootable and successful.
Forty post-reboot samples retained ACM, NCM, ping and SSH. Two separate host
opens of `/dev/ttyACM0` each sent a unique marker and received both that marker
and `6.17.0-sm8150-hotdog-clean`, proving bidirectional operation and reconnect.

The final offline r10/r38 full image is 4,500,488,192 bytes with SHA256
`b3b5b868814fb8a5b22ca7318e63578047cad3866abca5bdbd66ba6d0bbc21d4`.
Its matching AVB boot image is 100,663,296 bytes with SHA256
`aefe936e6fac4f1ee114f009d5d81fd7d7dfe8f7ab05b0a1ef2b0053c796e400`.
GPT generation, physical expansion metadata, both filesystem checks and AVB
verification pass offline.
